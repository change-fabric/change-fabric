# skills

Canonical source for system-wide Claude Code skills and hooks. What's installed is what's here.

## Rules

- Hooks fail silent: parse stdin via `HookEvent.read`, never crash.
- `install.rb` makes the live install match this repo. Re-run after pulling.
- Merging to `main` stages work; nothing is released until the matching tag is pushed. Three independent tracks: the toolkit (`skills/vX.Y.Z`, publishes a GitHub Release), the spec (`ChangeSchema::VERSION`, `spec/vX.Y.Z`, publishes a GitHub Release from that version's `CHANGELOG.md` section), and the site (`site/VERSION`, `site/vX.Y.Z`, deploys production). The toolkit has no version file at all: the tag is the version, picked by whoever cuts it, and `release-skills.yml` rejects anything that is not plain semver strictly above every existing `skills/v*` tag. There is nothing to bump in a toolkit PR. The other two tracks do carry a version file, bumped (semver) in the PR that changes them. A spec release never deploys the site, but a site deploy fails unless its spec version is already released, so the site may lag a spec release and never lead one. Tags are pushed by a human, never by a workflow. The full model and runbook is `RELEASING.md`.
- Squash merge. The maintainer merges every PR manually, do not merge unless told.
- No AI-slop glyphs in any authored output (commits, PRs, comments, prose, code): no em-dash, bullet, ellipsis, or smart quotes. `glyph_guard.rb` denies them at PreToolUse; `CF_ALLOW_GLYPH=1` is the escape hatch.
- Project services run in containers, never host daemons. `docker_doctrine_guard.rb` denies a Bash command that starts a service as a Homebrew or host daemon (`brew install/services` for a known service, a bare `redis-server`/`caddy run`, etc.) at PreToolUse; `CF_ALLOW_HOSTDAEMON=1` is the escape hatch. `doctrine_digest.rb` states the session-global tenets (this plus the slop rule and the PR-length rule below) once at SessionStart. The full rubric is `skills/docker/SKILL.md`.
- PR titles <= 60 chars. PR descriptions <= 640 chars, unless a bona fide reason needs more (a code snippet, a test-plan checklist); the core description should still stay inside 640 chars even then. `doctrine_digest.rb` states this as a session-global tenet at SessionStart; `slop_remind.rb` already prompts at `gh pr create`/`gh pr edit` time.
- A push or PR is gated on a completed design review of the files changed this session; `review_gate.rb` denies at PreToolUse until released. Run the review it hands back, then `ruby ~/.claude/cf/bin/review_ack.rb <session_id>` to record the verdict and release the gate. The round cap (5) is the escape valve.
- This toolkit is shared across projects: no specific client, customer, or downstream-project name/domain in any authored output in THIS repo. `client_name_guard.rb` denies at PreToolUse when authored text matches a term in the user's own `~/.claude/cf/sensitive_terms.txt` (one term per line, never committed here); `doctrine_digest.rb` restates the rule at SessionStart. Both are scoped to this repo's own remote (a client's own repo mentioning its own name is normal, not a leak) and stay silent everywhere else the toolkit is installed. `CF_ALLOW_SENSITIVE_TERM=1` is the escape hatch.
- A `gh pr merge` into a repo's protected branch (staging/production, per that repo's root `CHANGE.md`) is gated on a passing comprehensive `cf:change` run recorded for the PR's head SHA, and on the repo's own admin-bypass policy; `change_merge_guard.rb` denies at PreToolUse. Pushing a protected release tag (`tag:<glob>` promotion rules, a trunk+tag topology) is gated the same way at the moment of publication - a `git push` of the matching tag, or `gh release create` - by `change_tag_guard.rb`, also at PreToolUse, sharing the same gate question via `change_gate_check.rb`. Only a repo carrying a `CHANGE.md` is governed; a repo with no tag rules is unaffected by the tag guard. Both guards share one escape hatch: `CF_ALLOW_UNGATED_MERGE=1`, but only if exported before the session's own hook process started; it cannot be set from inside an agent session. When it genuinely cannot be set in advance, the reachable substitute is `ruby ~/.claude/cf/bin/change_override.rb <sha> --reason '<why>'`, run by a human from their own real terminal (it refuses without a real TTY, so an agent cannot run it on the human's behalf) to record an auditable, sha-scoped override both guards check. The `cf:change` platform (one file per repo, the root `CHANGE.md`, whose frontmatter carries both `change_config:` and `change_policy:`; four dockerized audit lanes) is `skills/change/SKILL.md`.
